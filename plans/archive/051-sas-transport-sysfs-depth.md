## Why this matters

Every sysfs read in the lsiutil backend was written against a directory layout
that **SAS-transport cards do not have**. The kernel's SAS transport class
inserts a `port-H:P/end_device-H:P/` pair between a host and its targets, and
splits device attributes across two sysfs classes that share the same
`end_device-H:B` naming. Four separate reads assume neither of those things.

The consequences on a real LSI SAS9207-8i (issue #14): the HBA Health tab's
Topology indicator reads *"Unknown — No drive count available"* forever, and
every drive's SAS address comes back blank with its PHY number silently
falling back to the SCSI target ID — which on that reporter's box is **wrong
for six of its eight drives**.

The reason this shipped is the part worth fixing hardest: `tests/health_sh_test.sh`
builds its fixture in the layout the code assumed, and comments that the shape
"mirrors real mpt2sas sysfs". It does not. The test is green, has always been
green, and certifies a topology that does not exist on the hardware this plugin
is for. **Fix the fixture first**, or you will fix the glob against a test that
cannot tell you whether you succeeded.

### Defect A — wrong sysfs class (`get_attached_drives.sh:38-51`)

```bash
    # ── Stage 2: SAS address + PHY from sysfs ────────────────────────────────────
    # /sys/class/sas_end_device/ exists on kernels with SAS transport (mpt3sas).
    if [ -d "/sys/class/sas_end_device" ]; then
        for ed in /sys/class/sas_end_device/end_device-*/; do
            [ -e "$ed" ] || continue
            sas=$(sed 's/0x//' "${ed}sas_address" 2>/dev/null | tr '[:lower:]' '[:upper:]' | tr -d ' \n')
            phy=$(tr -d ' \n' < "${ed}phy_identifier" 2>/dev/null)
            [ -n "$sas" ] || continue
            blk_dir=$(find -L "${ed}device" -maxdepth 12 -type d -name 'block' 2>/dev/null | head -1)
            blk=$(ls "$blk_dir" 2>/dev/null | head -1)
            [ -n "$blk" ] || continue
            printf "/dev/%s %s %s\n" "$blk" "$sas" "${phy:-0}"
        done
    fi > "$TMPSAS"
```

`sas_address` and `phy_identifier` are not in that class, so `$sas` is empty and
`continue` fires for every device. `$TMPSAS` is empty on every mpt*sas box.

**What that actually costs — the issue's analysis gets this wrong.** It claims
the Drives tab shows "no drives found". It does not. `parse/drives_join.sh`
iterates the *OS map* (`$TMPOS`, from lsiutil) and degrades gracefully when the
SAS map is missing:

```awk
        sas=(dev in sasmap) ? sasmap[dev] : ""
        # SATA drives have no sas_end_device entry; target == PHY for direct-attached
        phy=(dev in phymap) ? phymap[dev]+0 : tgt
```

So drives still render — with a **blank SAS address** and **`phy` silently set
to the SCSI target ID**. On the reporter's own box those differ:

| target | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| real phy | 3 | 0 | 1 | 2 | 5 | 4 | 6 | 7 |

Six of eight wrong. Everything keyed on the PHY↔drive join — the PHY Health
tab's `/dev/sdX` labels, the bay map, locate — points at the wrong drive, with
no visible sign that it is guessing. **That silent fallback is the real damage
of this defect**, and it is worse than the symptom the issue leads with.

### Defect C — trailing slash in Stage 3 (`get_attached_drives.sh:53-71`)

```bash
    # ── Stage 3: sysfs fallback if lsiutil -a 42,0 returned nothing ──────────────
    if [ ! -s "$TMPOS" ]; then
        for h in /sys/class/scsi_host/host*/; do
            proc=$(cat "${h}proc_name" 2>/dev/null)
            case "$proc" in mpt3sas|mpt2sas|mptsas) ;; *) continue ;; esac
            hn=${h%/}; hn=${hn##*host}
            for t in "${h}device/target${hn}:"[0-9]*/; do
                [ -d "$t" ] || continue
                IFS=':' read -r _ ch tg <<< "${t##*/target}"
```

`${t##*/target}` leaves the glob's trailing slash attached, so `tg` is `"0/"`
rather than `0`.

**The issue's analysis claims this collapses every target ID to 0 and collides
all drives. That claim is false — I ran it:**

```text
$ printf "%d_%d\n" "0" "3/"
bash: line 1: printf: 3/: invalid number
0_3
```

Bash parses the leading digits and uses **3**. Nothing collides. The real defect
is a stderr warning per drive plus a non-zero exit from `printf`. Worth the
one-character fix; **not** a data-corruption bug, and it must not be described
as one in the commit message.

**The larger problem in this same block, which the issue missed entirely**: that
`${h}device/target${hn}:` glob makes the *same* wrong-depth assumption as Defect
D below. On SAS-transport hardware it matches nothing, so Stage 3 — the fallback
that exists to rescue a failed `lsiutil -a 42,0` query — is **completely dead on
exactly the cards it was written for**. Fixing the trailing slash alone leaves
it dead. Step 3 fixes the depth.

### Repo conventions that apply here

Quoted from `ARCHITECTURE.md` — the executor has not read it:

- **"Windows/NTFS forbids `:` in filenames. Fixtures needing SCSI or PCI
  addresses in a path must be generated at runtime under `mktemp -d`, never
  committed — MSYS silently substitutes a lookalike character and git stores the
  mangled bytes."** Every fixture in this plan is built with `mkdir -p` at test
  runtime. **Never commit a directory containing `:`.**
- **"Mutation-test a new guard. Break it deliberately and confirm exactly the
  intended case fails. Several tests in this repo pass whether or not the code
  works until you check that."** Step 5 is that mutation test, and it is not
  optional — this whole plan exists because a test passed without proving
  anything.
- **"Absence is not health. Unknown, unmeasured and stale states must render as

  measurement."** `_drive_count` returning `0` must keep meaning "unknown"
  downstream; do not "improve" `health.php` to treat 0 as ok.
- **"Fixtures are evidence, not editable test data."** The layout you build in
  Step 1 comes from the `readlink -f` output quoted above, not from imagination.
- **"The SAS2 path has almost no hardware coverage."** Fixture tests are the
  only safety net you have here. Write them first.

### Step 4: Fix `_drive_count` and correct its comment (Defect D)

## Maintenance notes

- **This cannot be verified on the maintainer's hardware.** His box is
  SAS3/storcli; every line this plan touches is on the lsiutil path.
  `ARCHITECTURE.md` already flags that the SAS2 path is "fixture-tested only and
  effectively verified by reporters on the issue tracker", so the fixture *is*
  the safety net here — which is exactly why Step 5's mutation testing is a done
  criterion rather than a nicety. Ask @jac2424 on issue #14 to confirm on the
  9207-8i, and flag the change in the release notes.
- **The reusable lesson is Defect E, not any of A–D.** A fixture invented from
  an assumed layout will certify that assumption forever, and a green suite then
  reads as evidence. When adding a sysfs fixture, derive the shape from a real
  `readlink -f` or a diagnostic bundle — `scripts/bundle_support.sh:390-399`
  already collects exactly these listings, so a reporter's bundle is the cheapest
  source of truth available.
- **Two sysfs classes, one name.** `sas_device` and `sas_end_device` both
  contain `end_device-H:B` entries and neither errors when you read a missing
  attribute — you get an empty string and a `continue`. Any future sysfs read
  should assert it got a value rather than skipping silently; the silent skip is
  what let this run undetected across every release.
- **Deliberately deferred**: `parse/drives_join.sh`'s `phy = tgt` fallback stays
  in place. It is correct for SATA drives, and once Stage 2 works, SAS drives no
  longer reach it. If a future change makes that fallback reachable for SAS
  drives again, it should emit a distinguishable value rather than a plausible
  wrong one — but that is not this plan's fight.
- **Watch in review**: that `find` never regains `-L`; that no `-path` pattern
  with a wildcard crossing `/` is used to count block devices; and that
  `_drive_count` still returns `0` (not an error) for an absent host, since
  `health.php` depends on `0` meaning "unknown".
